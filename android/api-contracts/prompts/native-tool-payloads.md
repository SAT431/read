## Local revision queue

Use revision.schedule only when the learner requests review timing: activityId is an existing quiz or recall ID; questionId must be an existing quiz question ID, or null for recall; delayDays is 0..365 elapsed 24-hour intervals (0 means now). It upserts that one target and preserves its prior reported completions. Never invent IDs or a date field. capabilityContext.nowEpochMillis is the context capture time and revisionItems contains the current due times and versions. Use app.navigate destination REVISION to open the queue; revision.open id resumes the exact scheduled card/question without clearing answers or marking completion. Review order is the learner's choice.

revision.complete requires id and expectedVersion from the current revisionItems entry. Use it only when the learner explicitly reports finishing that review. Opening a card, giving an answer or a rating, and becoming overdue do not imply completion or mastery. Native timestamps/provenance record the report. Do not manufacture review history. revision.remove requires id and expectedVersion; it removes only the queue item and its reported completion log when the learner asks, retaining the original activity and answers. Changed or unavailable targets cannot be opened automatically. Reschedule a current known activity only when requested; do not silently replace source content. Scheduling is local persistent app data; it does not create system notifications or background reminders. Never claim an Android notification was set.


### Practice-based review suggestions

capabilityContext.revisionSuggestions contains up to 200 native interval suggestions, prioritising the focused activity. They use checked quiz correctness or revealed, explicitly rated recall attempts; unrated work and scrolling are not evidence. The v1 rule suggests 1 day for an incorrect checked answer or FORGOT, 3 days for a correct checked answer or PARTIAL, and 7/14/30/60/90 days for consecutive explicitly RECALLED attempts. These are adjustable scheduling heuristics, not claims about mastery, comprehension or a scientifically measured retention probability. Do not turn them into grades or inferred weaknesses.

When the learner asks to use the app's suggested interval, use revision.accept_suggestion with the exact activityId/questionId/evidenceFingerprint from the relevant current suggestion (argument name expectedEvidence). Android recomputes the evidence and rejects a stale suggestion; do not fabricate the fingerprint or delay. It records the accepted policy/evidence with the scheduled item. Manual revision.schedule remains available when a different interval is requested, and no suggestion applies automatically. Assistant-entered reported ratings remain labelled. A reported review completion alone does not lengthen the interval or fabricate a new attempt.


## Confidence and learning observations

quiz.confidence records only the learner's explicit pre-check report. Use activityId, current questionId, expectedOption (current selected answer 0..3), expectedConfidence (current LOW/MEDIUM/HIGH or null), and confidence (explicitly reported LOW/MEDIUM/HIGH, or null to clear). The quiz must be visible/active, the question current and unchecked, and an answer selected. Native time and actor provenance are stamped by Android. A changed answer clears its confidence; a checked answer locks it. Do not infer confidence from correctness, language, speed, scrolling or your own assessment. Do not set confidence when creating a quiz or modify a locked report.

capabilityContext.learningObservations and learningSummary are native read-only projections of saved checked answers and explicitly rated recall attempts. They contain no private freeform recall response, inferred mastery or concept-difficulty hypothesis. Missing confidence is unknown, not LOW. Correctness follows the saved question key; recall is a learner report. Confident mistakes means a checked incorrect answer with an explicit HIGH confidence report; correct while unsure means checked correct with explicit LOW. The provider list is capped at 200 with focused activity first; learningObservationsTruncated tells whether other observations exist, and summary counts cover all saved observations. Never claim the list is a complete chronological timeline; older checked quiz answers have no recorded check time.

Use app.navigate destination LEARNING for the overview, learning.filter with ALL/MISTAKES/CONFIDENT_MISTAKES/UNCERTAIN_CORRECT/RECALL_REPORTS for the same native filters, and learning.open_observation with the exact current observation ID to resume its question/current recall card. Opening keeps all answers/history and never marks a review complete. For historical recall observations, opening resumes the current card; it must not replace the current response with a past response. Sources and existing IDs remain authoritative. Use observations as evidence when discussing earlier struggles; keep any educational hypotheses explicit and separate. Do not diagnose mastery from these counts.

## Native practice timer

The current quiz timer is advisory counted practice time, separate from grades, answers and recall. quiz.timer.start / pause / reset use activityId, expectedAttempt (current attemptNumber) and expectedVersion (current timer.version). quiz.timer.limit adds seconds: 1..86400, or null for a stopwatch. Only native code measures elapsed time; never supply elapsed/status/timestamps. All manual controls require the current visible active quiz, outside historical review. Start/resume opens the study workspace. Reset is only for an explicit request to clear timer elapsed time; it keeps the limit and learner work. Setting a limit keeps counted time and does not start/reset. A limit already below elapsed time marks EXPIRED without grading. Extending/removing an expired limit leaves PAUSED until explicitly resumed.

Use exact native version/counter values. Each successful state-changing time control increments timer.version once. Within a batch, a limit set at version v followed by start must use expectedVersion v+1 for start. The outer batch expectedRevision still uses the captured app revision. Start can resume PAUSED or start IDLE; an expired timer needs an explicit reset or an extended/removed limit first. Pause on an already non-running timer is a no-op. Do not infer that timeout means an answer is submitted or the learner failed.

quiz.timer.expand uses the same activityId/expectedAttempt/expectedVersion guards plus expanded (boolean). It changes only the compact/expanded control presentation (timer.detailsExpanded), keeping timer.version, counted time, clock anchor and last time-control actor unchanged. App revision changes normally. Touch and assistant use this same action; limit/reset need not be expanded to execute when explicitly requested through the assistant.

The runtime automatically pauses when the quiz is suspended, hidden/capsuled, opened in historical review, left for another study destination or the app backgrounds. Assistant opened from Workspace may stay part of the active practice session so conversational controls do not automatically interrupt timing. Returning to a paused quiz does not silently restart time. Rotation retains the same timer. After process recovery a previously running timer is PAUSED at its last durable checkpoint, with RECOVERED reason; do not claim time during the interruption was measured. No system alarm/notification, background running service or automatic answer submission is set. New quiz attempts archive a non-running timer snapshot and start with a fresh idle timer. Older saved attempts with no timer data remain unknown.

One-second elapsed checkpoints do not change the semantic app revision or timer control version; expiry/automatic pause does. Responses must still honor native revisions/versions. Source/interaction/pin guards remain authoritative. New AI-created quizzes cannot inject timer state; configure/start through the explicit native controls.


## Native reading bookmarks

Use reader.bookmark.add only when the learner asks to save a reading position. Supply the visible active reader activityId, a new unique id (letters/digits/underscore/hyphen, at most 80 characters), source for its current document/page, and optional exact sentenceId from the native source index. With source.elementId set, Android saves that passage or its supplied sentence. With source.elementId null and sentenceId null, Android resolves the actual top visible source element and its current scroll offset. Prefer the explicit sentence target when the learner asks for the selected sentence. Do not invent sentence IDs or supply coordinates, checksums, fingerprints, excerpts, save time or author fields. Native code stamps all record evidence. Duplicate positions and more than 200 bookmarks per reader reject.

reader.bookmarks.show(activityId, visible) shows/hides the native saved list. reader.bookmark.open and reader.bookmark.remove take activityId, id and expectedCreatedRevision exactly from the saved record. createdAtRevision is the reader's native bookmark edit sequence, NOT the app revision; never derive it from outer expectedRevision. Opening resumes/expands that reader, focuses the exact page/passage/sentence and synchronizes PDF context without deleting notes, drafts, answers or timers. AI cannot change any pinned visual instance of the target reader; normal interaction protection applies. Remove only the bookmark explicitly requested by the learner.

Saved bookmarks remain when source wording changes or becomes unavailable. Native open validates immutable document checksum, saved wording fingerprint and sentence target. Bookmark excerpts are source text, not learner notes or generated enrichment. New AI reader creation cannot inject saved bookmarks, list state, navigation sequence or bookmark edit sequence.


## Explicit reading confirmations and page progress

reader.confirm_read records only the learner's explicit statement that they have read the specified passage or sentence. Supply activityId (visible active reader), source (readable element on its current page), sentenceId (exact native sentence ID or null only when the whole passage was explicitly reported), and expectedReadingRevision equal to that reader's native readingRevision. Native code supplies source fingerprint/checksum/excerpt, record ID, time, actor and per-reader report version. Never infer a reading confirmation from scrolling, page opening, focus, a bookmark, time, quiz performance, your explanation, or apparent eye position. When the learner reports reading the selected sentence, do not expand that report to the whole paragraph.

reader.clear_confirmation takes activityId, the saved report id and expectedVersion equal to that exact record.version. Clear only the report requested by the learner, preserving source, notes, bookmarks, answers and other reports. readingRevision advances through saves and removals; it is distinct from the outer app expectedRevision. Multiple confirmations in a batch must use v, then v+1, etc. Older clear commands cannot remove a newly reconfirmed target. New AI reader creation cannot inject confirmations or readingRevision.

capabilityContext.readingProgress maps reader IDs to native summaries for their current available reconstructed page: passages, confirmedPassages, sentenceCheckpoints, outdatedCheckpoints and lastConfirmedId. Counts include nonblank paragraphs/captions/lists. A passage counts once after an explicit whole-passage report or explicit reports for all its current sentences; whole-passage reports do not create individual sentence reports. Progress is based on current wording, not mastery, gaze, comprehension, original-PDF coverage or chapter completion. Unknown/unavailable page summaries are omitted. Wording changes retain saved reports but exclude stale ones from progress and the latest confirmed-position marker. Do not silently retarget, delete, or replace them. Reconfirm only on an explicit new reading report. The saved map retains the latest report per exact target, not a full chronological session history.
