# Bounded multi-step assistant requests

Updated 16 October 2026. Follow-up: PAGE_PREPARATION_CONTINUATION.md now connects exclusively native page-engineering effects when the current await capability flag is true. Earlier waiting descriptions below describe the initial bounded-continuation milestone. Implemented, installed in place and verified with focused runtime/tablet/live checks. This extends native study search: one user Send can search and then open the matching native result using fresh context.

## Behavior

MentorResponse has an additive optional continueAfterExecution Boolean, default false. A model can ask for another round only with a valid batch. After that whole batch is accepted, durably acknowledged and has no platform effects, the native session refreshes state and waits for local search projection when needed before requesting another response. Request IDs, expected revisions, enabled capabilities, library/source identity, pins and writing guards are validated independently for every batch. A changed user view stops the old continuation. Protected writing rejects app mutations but can still receive a plain reply without moving/changing the workspace.

The user supplies one intent. Each request permits at most three provider rounds and a 90-second overall deadline, including readiness waits and existing per-call transport limits/retries. A round can use the existing at-most-24-command batch. The model must stop when the requested intent is fulfilled, clarification is needed or no supported next step remains. This is bounded continuation over native tools, not arbitrary agent code, unlimited replanning or a fixed study sequence.

The status bar shows the native step count during later rounds, and Cancel remains available before execution. Accepted earlier batches remain applied if a later round fails, times out, is cancelled or rejects stale context; layout/learning work is not silently rolled back. Native failure text distinguishes earlier retained work from a latest-step failure. Android dialogs, microphone requests, repair previews and background engineering stop automatic continuation and produce WAITING when the model requested more steps. Acceptance of such an effect does not mean the picker result, OS permission, repair approval or processing completion happened.

## Retry, recovery and native ownership

Conversation state records bounded accepted action IDs, round, retry safety and the last acknowledged workspace revision. Execution-result records also include native action IDs/origin/revision. Request context describes prior acceptance and whether a request resumes after failure. These are native records, not a model's self-reported success. Every round still uses the original utterance and fresh native source/capability context; the user message is not duplicated for internal rounds.

A failed request can offer Continue request only after safe absolute navigation/read steps. Relative next/previous/back moves, learner mutations and platform effects disable replay retry. A partial safe retry also requires the same native workspace revision as the last accepted step; a manual study change requires a new intent rather than replaying the old scope. A later safe retry receives current search results and prior acknowledgements to finish the remaining step. This is not a general exactly-once transaction across multiple model responses.

Before a commit, native history is checkpointed as EXECUTING. Once committing starts, workspace durability/effect acknowledgement finish within the existing non-cancellable section. A failure to save the accepted acknowledgement stops before another provider call and disables retry. Process recovery of an interrupted EXECUTING record never replays it. Interrupted REQUESTING state retains known acceptance; unsafe prior changes do not gain a Retry button. Atomic history records remain app-private and outside cloud backup in production. Additive defaults preserve old single-step/history records; bounded metadata validation rejects malformed history without overwriting the original.

The runtime was split into four focused owners alongside AssistantSession: AssistantRequestBuilder, AssistantConversation, AssistantRoundRunner and AssistantContinuationPolicy. No feature module imports a provider or mutates the workspace directly. Direct Gemini response decoding and its serializer-derived schema support the new optional Boolean; a continuation with no batch is rejected. Existing direct Gemini 3.5 Flash-Lite/Groq/Keystore architecture remains unchanged. The model prompt documents continuation, non-replay and platform/source boundaries. Private draft/search redaction, native-only approvals and all prior command guards remain active.
